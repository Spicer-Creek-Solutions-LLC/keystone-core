# Dossier — C02, SQLite migrations and durable ledgers

The second Stage C task, and the first that makes anything survive a restart.

C01 built a protocol that holds a job identifier and a lifecycle state; nothing
yet writes either down. `ADR-0008` decided **two stores with no abstraction over
them** — a server store and an agent ledger — and assigned *"migrations, SQL and
the implementation"* here by name. C02 builds them.

**It is a persistence task with no transport and no execution.** NATS arrives at
C06 and a process tree at C07. Nothing here connects to a broker, opens the
operator socket, or creates a child.

This dossier is a boundary, not an approval. Landing it authorizes nothing: C02
still needs its own presented plan and explicit approval, and it is a
**behaviour workstream**, so it splits into `C02-A` and `C02-I` with different
agents per [`REBOOT-EXECUTION-PLAN.md`](../project/REBOOT-EXECUTION-PLAN.md)
§ "Required task dossier". Roles alternate from C01: **`C02-A` is Claude's to
write and Codex's to review**, and `C02-I` the reverse.

**One file, two tasks**, as C01 established. § 3.1 and § 3.2 state each half's
outputs separately, because the line between them is the thing most worth
reading in one place.

## 5. Acceptance cases

### 5.1 The `TESTING.md` feature table

C02 crosses no NATS transport, starts no agent process and executes nothing, so
the transport, execution and journey rows are `N/A`. **Durable state is the one
row it owns**, and the restart boundary is where it is paid.

### 5.2 The contract's cases

| Case | Fails when |
|---|---|
| `AC-1` | A migration runs out of order, or runs backwards |
| `AC-2` | A partially applied migration does not leave the store at its last complete step |
| `AC-3` | A migration spans both stores, or a combined version exists |
| `AC-4` | **Receipt and start commit in one transaction** |
| `AC-5` | A crash between receipt and start is indistinguishable from a crash before either |
| `AC-6` | Job identifier and accepted request do not commit together before publication |
| `AC-7` | Terminal state and result do not commit together |
| `AC-8` | The result `PubAck` is not its own write |
| `AC-9` | The ledger cannot be read without the server, at the documented path |
| `AC-10` | The shipped schema and the published schema differ |
| `AC-11` | A store or its directory has the wrong owner or mode |
| `AC-12` | A retention floor is breached, or a record is deleted before it |
| `AC-13` | A corrupt store is opened and served rather than refused |

**`AC-4` and `AC-5` are the pair that matters**, and § 5 says why: if receipt and
start commit together, `ADR-0006`'s recovery rule collapses into
`Indeterminate`. `AC-4` checks the schema's shape; **`AC-5` checks the
consequence**, and only the second can fail for the right reason.

### 5.3 Demonstrated failing, and what these cases cannot detect

Every case is demonstrated against a planted defect before it is trusted, per
`DL-1`. **C01 established that this is not sufficient**, and the lesson carries:

- **A check cannot fail on an input nobody looks at.** C01 produced four
  instances — a signed-input test blind to an omitted region, a round-trip blind
  to an unbound KDF transcript, a fixture that never held a cleartext
  correlation identifier, and a zero nonce that passed every structural check
  because none read the value. `C02-A` asks of each case: does the fixture
  contain the input, and does anything read the value rather than the shape?
- **What these cases cannot detect.** That the schema is the *right* schema for
  a journey no task has yet written; that retention is long *enough*; that a
  corrupt store was corrupted by a defect rather than a disk. `DL-2` is the
  ledger entry for the first of those.

## 11. Decisions requiring confirmation at C02 approval

### `D-C02-1` — the driver, and the module's first dependency

`ADR-0008` names no driver and no cgo policy. **The module has zero
dependencies today**, so this is not a routine addition, and
`feedback_comparison_plans_for_deps` means it needs evidence rather than an
inherited habit.

**The archive is not authority.** `CAP-STORE-003` records that Generation 1 used
`modernc.org/sqlite`; RFC 0001 makes that research.

| Option | Evidence |
|---|---|
| **`modernc.org/sqlite`** (pure Go) | Builds and runs under `CGO_ENABLED=0`; SQLite 3.53.4. **1 direct + 9 indirect modules**, 25 in the full graph; a trivial binary using it is 9.5 MB |
| `mattn/go-sqlite3` (cgo) | **Ruled out.** `test/e2e/docker/Dockerfile` builds with `CGO_ENABLED=0`, so the container suite could not build it |
| No SQLite | **Not available.** `ADR-0008` § 1 decides SQLite for both stores |

**Proposed: `modernc.org/sqlite`.** The cgo constraint is decisive and the
alternative does not exist. What is worth confirming rather than assuming is the
**cost**: ten modules entering a tree that has had none, a 9.5 MB floor on every
binary, and `make vuln` now having a supply chain to scan.

### `D-C02-2` — the ledger schema is a published interface, with a gate

`ADR-0008` § 3 says the ledger is *"SQLite with a published schema, at a
documented path, readable by root on the host"*, and **removes a qualifier from
`RSK-4` on that basis** — the compensating control used to read *"the operator
reaches those ledgers only through the server"*.

So the publication is not documentation. **It is the mitigation.** If C02 ships
a schema and does not publish it, or publishes one that drifts, a threat-model
row becomes silently false — and nothing in the tree would report it.

`AC-10` compares the shipped schema against the published one and fails on
difference. **A promise in prose is not what `RSK-4` can rest on.**

### `D-C02-3` — the receipt/start separation needs a crash, not a schema

§ 5 requires receipt and start to commit **separately**, because if they commit
together a crash between them is indistinguishable from a crash before either.

A schema cannot show that. Two separate `INSERT` statements in one transaction
look identical to two in two transactions at rest; the difference appears only
when the process stops in between. So `C02-A` builds a harness that **stops a
store at a chosen commit boundary and reopens it**, and `AC-5` asserts the two
crashes are distinguishable.

This is `ARCH-JOB-002`'s restart boundary suite, which `TESTING.md` schedules at
**merge to `main`** rather than per pull request.

### `D-C02-4` — reuse C01-A's contract machinery, do not build a second

C01-A built a frozen acceptance surface, a mutable `pending-requirements`
manifest, an expiry check tied to the epic's ticks, and an immutability guard.
**All of it is general.** C02-A extends the manifest and adds a second contract
package; it does not invent a parallel mechanism.

The one thing to verify rather than assume was `pending-contract`'s coupling to
a single package. **`G39` settled it, and with a better answer than this
decision proposed.**

This said case identifiers need a package-qualified form — `C02/AC-1`. They do
not. The tool now **enumerates `test/contract/*/pending-requirements.json` and
scopes each manifest's identifiers to its own package**, so two packages may
both register `AC-1` and the directory qualifies them. There is no naming scheme
to remember.

The coupling was also wider than this decision said: a hardcoded case-to-test
map, a hardcoded manifest path, and a hardcoded package passed to `go test`.
`D-C02-4`'s instruction stands — **reuse C01-A's machinery, do not build a
second** — and that machinery now works for more than one package.
