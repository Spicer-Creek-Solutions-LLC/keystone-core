# Dossier — P09, Local operator API and authorization ADR

The task that decides how a human reaches the control plane, and what the
control plane records about them. Every ADR in Stage P has deferred its
operator-facing half here — `ADR-0003` for who may create a token, `ADR-0004`
for which operators may do what, `ADR-0005` for the error an operator sees,
`ADR-0006` for how a lifecycle state is rendered, `ADR-0007` for how a refusal
and a truncation are shown, `ADR-0008` for how a retrieved record is presented,
and RFC 0003 for how a harvest fallback surfaces. § 2 enumerates them.

demonstrate any of this and P11 builds the repository that could hold it.

## 3. Exact outputs

One ADR, deciding these and nothing else:

1. **The socket** — path, owning user, owning group, octal mode, and the mode of
   the directory containing it. Which trust domain owns the file.
2. **Who may connect**, as an enumerated principal set rather than a permission
   bit: the configured admin group, plus root, which bypasses mode checks.
3. **Where authorization is evaluated** — on `accept()`, from peer credentials
   obtained from the kernel, **before any request byte is parsed**. Stated as an
   ordering obligation, in the shape `ADR-0006` § 3 uses for durability.
4. **What an operator may do**, as the charter's seven journeys mapped to the
   authority each requires. In this release every row is the same value, and the
   enumeration rather than the values is the decision.
5. **Exit code placement** — where `10` is returned and where it is not, and what
   a caller sees when the kernel refuses the connection outright.
6. **The audit identity** — what fills `ADR-0008` § 6's **Actor** field for an
   operator, which part of it is authoritative, and which part is a snapshot.
7. **Impersonation boundaries** — that no request field may set the acting
   identity, and what that forecloses.
8. **Stale-socket recovery** — what happens to a socket file left by a crashed
   server, and why unlinking one indiscriminately is a hijack.
9. **Request limits and framing** — including limits that apply to connections
   that have not yet been authorized.
10. **`RSK-8`'s disposition**, with the compensating control restated against
    what P09 actually provides.
11. **What the operator API must never become** — `ARCH-COMM-001`'s clause that
    it *"must not become a hidden agent transport"*, expressed as a property
    rather than an intention.
12. **Deferred decision points**, each with what would trigger it.

## 11. Decisions requiring confirmation at P09 approval

### `D-P09-1` — `RSK-8` expires here, and it cannot resolve

Distinguishing the operator from code running in the operator's session needs
attestation or a second factor. Neither is in Generation 2's scope and neither is
proposed, so **resolve is not available** and claiming it would be the statement
`DL-1` exists to catch.

**The disposition is renew, with the compensating control strengthened and the
exposure sharpened.** What P09 genuinely adds is that the actor is derived from
the kernel rather than from the request, so a caller **cannot forge an
attribution to someone else** — which the current control does not say and which
nothing currently guarantees. What P09 does not add is any defence against
malware in the operator's own session, which is still attributed to the operator
and always will be.

**The word "strengthened" must not be read as "smaller".** The row carries the
same distinction RFC 0004's `THR-54` had to make: **disclosure, not prevention.**
Without that sentence the renewal reads as comfort it has not earned.

The exposure is also more concrete than when `RSK-8` was written. After RFC 0003
"the operator's full authority" includes running argv as root on every enrolled
host, and under full admin one group membership carries token creation,
execution, cancellation and audit read together. `THR-35` predicted this — *"P09's
authorization model will share whatever authority the compromise holds"* — so it
is a forecast confirmed, not a widening.

**Expires at C04**, the first task that builds the socket and could show
peer-credential attribution actually working. The calendar date stays
**2027-03-13** rather than being extended: a renewal that also buys twelve months
is two decisions wearing one word.

### `D-P09-2` — "which operators may do what" resolves to "all of it", and the decision is the unit

Five sites defer this to P09 — `ADR-0003` § 1, `ADR-0004` § 13, `THR-24`, P04's
dossier and the glossary. The execution plan has already fixed the answer:
**full-admin authorization for the narrow first release; RBAC and remote operator
access remain Future.**

So the substantive question is settled before P09 opens, and answering those
five with one sentence would be accurate and would leave two things undone: the
audit record still needs an operation identifier, and a later RBAC would have to
invent a dimension rather than fill one in.

**P09 maps the charter's § 5 journeys — enroll, list and presence, run, status,
output, cancel, audit — to the authority each requires, and every row reads the
same value.** The enumeration is the decision; the uniform answer is this
release's policy.

**The table is sourced from the charter, not invented.** P09 defines no new list,
so there is one source of truth and the ADR's table is a projection of it. That
answers the objection that would otherwise apply — a second enumeration of the
journeys is a second thing to drift, and drift between two statements of one fact
is this project's most-recurring defect.

**A table whose every row is identical cannot disagree with itself**, which makes
it a `DL-1` trap. `AC-3` therefore asserts the projection is **total** against the
charter, which is a property that can fail, and not the cell values, which cannot.

### `D-P09-3` — authorization is evaluated on accept, from the kernel, before any byte is read

The charter delegates the placement: *"`10` applies to every command whose
invocation is subject to operator authorization; P09 defines where that is
evaluated."* Three placements were considered and the reasoning is recorded so a
P09 that wants a different one has to argue against it rather than around it.

**Authorization at the socket alone** — mode and group are the whole decision —
is the simplest thing that is true, and it fails `ARCH-OBS-001`. A caller the
kernel refuses is a caller Keystone never sees, so *authorization denial* has no
record. The defence is that an unobserved event is not a lifecycle transition.
That defence is available, and it also covers **an operator you just revoked**,
which is the denial that matters most.

**Authorization in-band, after reading the request**, makes `10` a real protocol
response and puts denials in the audit record — at the cost of letting
unauthenticated peers reach the privileged parser, which is the surface
`ADR-0007` § 7 split the agent apart to avoid.

**The chosen placement takes the first's surface and the second's
observability.** On `accept()`, the server reads the peer's credentials **from
the kernel** and authorizes before a single request byte is parsed. Peer
credentials do not come from the wire, so no untrusted input reaches the parser;
a denied caller gets a record, a fixed response and a closed connection.

**The socket stays restricted.** It is not opened widely to make denials
observable: the connectable set is an enumerated principal list — the configured
admin group, plus root, which bypasses mode checks — so an arbitrary local user
is still refused by the kernel and cannot flood the audit by connecting in a
loop.

**And the in-band check is still not redundant, for a reason that is not
hypothetical.** Supplementary group membership is **cached in a process's
credentials at login**. An operator removed from the admin group keeps that
membership in every already-running shell, so the socket's own permission check
lets them connect. Only the in-band re-derivation denies them — and a revoked
operator's attempt is precisely the denial an audit record is for. Root is the
second such case, and a misconfigured mode is the third.

The consequence, stated rather than discovered: **a principal with no access at
all is refused by the kernel and produces no record.** That set is people the
deployment never granted anything to, and the ADR must say so under `AC-6`
instead of letting the absence pass as compliance.

**`10` is returned where authorization is evaluated.** What a caller sees when
the kernel refuses the connection outright is `AC-4`'s second half, and it is a
real question: the charter describes `1` as *"Local or usage error: bad
arguments, unreadable configuration"*, and an `EACCES` on a socket is neither.

### `D-P09-4` — the audit record names a uid, and annotates a name

`ADR-0008` § 6's **Actor** field says only *"Who caused it"*. For an operator it
becomes **the numeric uid, which is authoritative, plus the username resolved at
the time, which is an annotation**.

A uid never changes meaning and is unreadable at three in the morning. A
username is readable and is **a claim about a moment stored as a fact**: delete
the account, reuse the uid, and the record now names the wrong person with
nothing in it to reveal that. Recording both keeps the identity stable and the
record legible, and marks which half is which.

**The ADR states in the schema that this is the identity exercised and not the
person.** `RSK-8` already concedes it, and a concession that lives only in the
risk register is invisible to the person actually reading an audit row.

The `SO_PEERCRED` triple's third element, the pid, is **not** recorded. It is
useful for minutes and aggressively reused thereafter, so storing it invites
exactly the over-reading this field is trying to prevent.

### `D-P09-5` — two normative documents disagree about who owns artifact redaction

`TESTING.md` § "Isolation and production paths" says **"P09 defines artifact
classification and redaction"**. `REBOOT-EXECUTION-PLAN.md` § P10 says
**"Define artifact classification and redaction. Seed private-key, token,
command, and output canaries and scan artifacts before CI upload."**

One of them is wrong, and P09 is the task that discovers it because P09 is the
task one of them assigns it to.

**The plan should win**: it is the sequencing authority, its P10 entry describes
the harness that would do the redacting, and redaction of CI artifacts has
nothing to do with an operator socket. On that reading `TESTING.md` is stale.

**P09 raises it and does not fix it.** `TESTING.md` is out of bounds in § 2, the
correction belongs to a `G` task or to P10's own dossier, and a P09 that quietly

### `D-P09-6` — the threat model puts the socket in the operator's domain

`AST-14` — the local operator API socket — is listed in `TD-OP`, *"the operator's
workstation: the `keystone` CLI, its configuration, the local API socket"*. But
`TB-1` makes the socket the **boundary** between `TD-OP` and `TD-SRV`, and it is
the **server** that creates the file and sets its mode.

This matters because it decides who may change the socket's permissions. If the
file is the operator's, a compromised workstation can widen it. If it is the
server's, it cannot.

P09 must **state which domain owns the file** (`AC-1`). Whether `AST-14`'s row
should move is a threat-model question; the row is in § 2's allowed sites, so
P09 may sharpen it, and moving an asset between domains is a change to P01's
model that should be argued at approval rather than performed quietly.
