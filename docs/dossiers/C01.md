# Dossier — C01, Protocol types and cryptographic vectors

The first task in Stage C, and the first code in this repository that does
something rather than reports what it would do.

`P11a` deliberately shipped three binaries with no behaviour —
`internal/cli/boundary_test.go` enforces that against the whole module. C01 is
where that boundary first moves. It implements [`ADR-0005`](../adr/0005-versioned-encrypted-protocol.md):
the nine-field envelope, the seven message classes, signatures, recipient
encryption, replay bounds, the refusal codes, and the **computed** test vectors
that every later behaviour task is measured against.

**It is a library task with no transport.** NATS arrives at C06. Nothing here
connects to a broker, opens a socket, or executes a process.

This dossier is a boundary, not an approval. Landing it authorizes nothing: C01
still needs its own presented plan and explicit approval, and it is a
**behaviour workstream**, so it splits into `C01-A` and `C01-I` with different
agents per [`REBOOT-EXECUTION-PLAN.md`](../project/REBOOT-EXECUTION-PLAN.md)
§ "Required task dossier". Program rule 6's separation is met by that split, not
by the reviewer in § 8.

**Two tasks, one dossier**, confirmed at approval; § 3.1 and § 3.2 state each
half's outputs separately.

**That reading is not what the documents say, and this dossier does not fix
them.** `REBOOT-EXECUTION-PLAN.md` § "Required task dossier" and
[`README.md`](README.md) § Naming both say *one file per task*, and the index's
`C05-A.md` example reads as a requirement to split. Both are out of this pull
request's § 2 and out of C01's § 3.3, and reconciling two source-of-truth
documents under a task approval is the move this dossier refuses on
`ADR-0005`'s behalf in § 1. **It needs its own task**, raised in the pull request
that lands this file.

### 5.2 The contract's cases

| Case | Fails when |
|---|---|
| `AC-1` | An envelope does not round-trip through encode and decode |
| `AC-2` | A framing vector's bytes disagree with `ADR-0005` § 1's field order or length prefixes |
| `AC-3` | A bit flipped in **any** of fields 1 through 8 is accepted |
| `AC-4` | A signature from the wrong key is accepted |
| `AC-5` | A class in § 7 is unsigned, or a class outside § 7 is accepted |
| `AC-6` | A truncated ciphertext, or one for the wrong recipient, is accepted |
| `AC-7` | An unknown version is accepted, or a known version with the wrong field sequence is accepted |
| `AC-8` | An unknown header is refused, or trailing bytes are refused where the signature still verifies |
| `AC-9` | A vector produced by one process is not verified by another |
| `AC-10` | A refusal is outside § 9's seven codes, or carries input-derived detail |
| `AC-11` | Two probing inputs that must collapse to one code return different refusals |
| `AC-12` | A golden vector's bytes change without a version bump |
| `AC-13` | A seed-corpus entry crashes the parser |

**`AC-3` is the one that matters most**, and `ADR-0005` § 10 says why: field 1 is
the protocol version, and a vector set that omits it leaves the downgrade
defence untested.

**`AC-11` is `D-C01-5`.** The pairs are: a bad signature from a known key and
from an unknown key; a truncated ciphertext and one for the wrong recipient; an
envelope malformed at field 2 and at field 7. Each pair must produce **identical**
refusals.

### 5.3 Demonstrated failing, and what these cases cannot detect

Every **applicable** case is demonstrated failing before it is accepted, per
`REBOOT-EXECUTION-PLAN.md`. The ten in § 5.1 are `N/A` and have no defect to
plant; their per-case rationale is the reviewer's subject, since **a wrongly
waived case is invisible to every demonstration**. A case that fires on every planted defect is not
discriminating and must be tightened.

| Case | What it cannot detect | What would |
|---|---|---|
| `AC-1`–`AC-8` | **A self-consistent wrong encoding.** An implementation that emits fields in the wrong order and verifies its own output satisfies every property | `AC-2`'s framing vectors, which is why they exist |
| `AC-9` | **Interoperability.** Both processes share one Go package, so a bug they share is invisible | A second implementation; nothing in this project provides one |
| `AC-10`, `AC-11` | **Timing.** Identical error values returned after measurably different work still distinguish the cases | Constant-time comparison, out of scope for C01 and named here rather than implied |
| `AC-12` | **Whether the frozen bytes were right.** Goldens are descriptive on the day they land | Review against § 1, and `AC-2` |
| `AC-13` | **Inputs nobody has found.** A corpus asserts no *known* input breaks the parser | Timed fuzzing, registered as owed by `D-C01-4` |
| All | **Whether the protocol is the right protocol.** These cases measure conformance to `ADR-0005` and say nothing about whether `ADR-0005` is correct | The independent reviewer, and C08 when the journey first runs end to end |

## 11. Decisions requiring confirmation at C01 approval

### `D-C01-1` — the contract asserts properties; the implementation computes the vectors

**Confirmed: properties, goldens frozen by `C01-I`, and hand-written framing
vectors in `C01-A`.**

`ADR-0005` § 10 forbids the obvious shape: *"a vector written by hand before an
implementation exists is a number the implementation will be tuned to match."* So
`C01-A` cannot hold expected byte strings for anything cryptographic.

Properties alone leave a hole — **a self-consistent wrong encoding passes every
one of them**, and the cross-process check does not help because both processes
share the bug. § 1's field table is fully normative and needs no crypto to
check, so `C01-A` also carries framing vectors with the signature field zeroed.
They are not cryptographic vectors, so § 10's warning does not reach them.

Three layers, three jobs: **framing vectors** say the encoding matches the ADR,
**properties** say the operations behave, **goldens** say nothing drifts later.

### `D-C01-2` — the `pending-requirements` manifest is designed here and built in `C01-A`

**Confirmed.** `REBOOT-EXECUTION-PLAN.md` requires a *"machine-checked
`pending-requirements` manifest with an owner and expiry"* and a separate
`pending-contract` target. **Nothing in the tree implements it.** P11 built the
analogous `Lands at` liveness for the register and called it *the shape the
execution plan already uses* — not the manifest itself.

The design is settled here because the semantics need review as design:

| Field | Meaning |
|---|---|
| Case | The exact contract case, named. Normal CI skips **only** this |
| Owner | The task that will implement it. Must be a task in the epic |
| Expiry | The task after which the entry is a **failure**, not a warning |
| Reason | Why the behaviour is missing |

**An entry is renewed by an approved change to the manifest, never by editing an
expiry in passing.** Liveness derives from the epic's ticks, as `archlint`'s does,
so there are no dates to maintain.

**The companion guard is built with it**: CI rejects `C01-I` editing the contract
at `C01-A`'s recorded SHA unless a separately approved specification pull request
changed it first. Deciding the manifest without it leaves half the rule unbuilt.

### `D-C01-3` — C01 pays cross-process serialization; the transport evidence moves to C08

**Confirmed.** Two problems, two answers.

`ARCH-COMM-003` requires *"released binaries, production configuration parsing,
production protocol serialization, and production NATS subjects."* **At C01 there
are no NATS subjects** — the protocol precedes the transport. C01 can pay the
serialization-across-processes half and structurally cannot pay the rest.

So C01 ships **a producer binary and a verifier binary, run as separate OS
processes** over files or stdio. Real address spaces, production serialization,
running in CI the day it merges. No broker and no `R6` dependency.

And `ARCH-NATS-006`'s two `test/e2e/docker/` rows **move to C08**. The invariant
is about three key layers being independent — transport identity, envelope
signing, payload encryption — and demonstrating that needs the broker in the
path. C08 is where commands and results first cross it. `archlint` makes the move
a checked change rather than a silent one.

**What was rejected:** writing the Docker tests at C01 and registering them
pending. `R6` is unmet with no owner and no diagnosis, and a pending entry
blocked on someone else's infrastructure is how a pending list becomes permanent.

### `D-C01-4` — seed corpus every pull request; the timed search is owed

**Confirmed.** `TESTING.md` schedules **no fuzzing at all**, so this adds a line
rather than picking a bucket.

`go test` runs seed entries as ordinary unit tests: deterministic, and for a
length-prefixed binary parser a growing corpus of every malformed-length input
ever found is exactly the regression surface that matters. **Timed fuzzing on
every pull request was rejected** — a fixed `-fuzztime` is a budget, not a
property, and a fuzzer that crashes on one run and not the next makes every pull
request a coin flip on a serial runner.

The **nightly timed search is registered as owed** and asserted by
`deferred-gates-check`, the way P11b asserts the container suite. Its blocker is
a schedule that does not exist rather than a machine that does not work.

### `D-C01-5` — § 9's coarseness is tested, including indistinguishability

**Confirmed.** § 9's seven codes are *"deliberately coarse"*: a sender must not
learn which key failed, whether an identifier exists, or where parsing stopped.

**The realistic regression is a well-intentioned one.** Wrapping a refusal with
`fmt.Errorf("...: %w", err)` reads as an improvement in review and hands an
attacker the structure offset. Asserting the set is closed would not catch it —
seven codes each carrying a parse offset passes, which is a check weaker than its
claim.

So `AC-10` asserts the closed set **and** fixed rendering, and `AC-11` asserts
indistinguishability. The middle pair is the one worth keeping: *truncated*
versus *wrong recipient* is an oracle telling a prober whether they hold a
ciphertext addressed to someone else.

This constrains `C01-I` to return a less specific code than it knows. That is the
intent, recorded here so it is a decision rather than a surprise.
