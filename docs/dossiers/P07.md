# Dossier — P07, Safe execution ADR

The task that decides what actually happens on the host. Every ADR before it
decided how a command travels, who may send it, what is inside it, and what the
system believes about it. P07 decides what the agent **does** with it, and it is
the last decision before the command becomes a process.

**P07 is not complete.** `ADR-0007` is proposed with one decision outstanding —
whether an operator naming `/bin/sh` or a `#!` script as `argv[0]` is inside
charter § 6. `ADR-0007` § 2.1 states both readings and decides neither, because
`D-P07-1` below forbids this task from widening the boundary by interpretation.
**C07 is blocked until it is settled**, since the two readings produce different
executors. The epic's P07 entry stays unticked for that reason.

This dossier is a boundary, not an approval. Landing it authorizes nothing: P07
still needs its own presented plan and explicit approval. P07 is a planning and
ADR task and may use one pull request; it does not split into `-A` and `-I`.
Program rule 6's separation of implementation from acceptance review is met by
the independent reviewer named in § 8.

## 3. Exact outputs

One ADR, `docs/adr/0007-safe-execution.md`, containing:

1. **Argv-only execution** — how a command becomes a process with **no shell interpreting its argv**, and why argv is a vector rather than a string (`THR-15`). A shell may run for the harvest of item 5 and never sees operator input
2. **Every excluded form charter § 6 lists**, each named and each stated as still excluded, with what a request for it produces — and **what `RFC 0003` admits**, with the conditions attached to each
3. **Deny-by-default** — the rule for an execution form the ADR does not name (`ARCH-EXEC-001`)
4. **Executable resolution** — how the program is located, and what `PATH` participation is permitted
5. **The environment** — the login-environment harvest `RFC 0003` admits: the fixed agent-authored command that runs it, its own timeout, where its output goes, the size bound, the fallback to the derived environment on failure or `nologin`, and **that the harvested environment never reaches an audit record**
6. **The fixed working directory** — what it is and what decides it
7. **Service identity and privilege** — what the agent runs as, and therefore what a command can reach (`D-P07-2`)
8. **Limits** — duration, output, concurrency and host resources, each with a value or an explicit statement that a deployment sets it (`ARCH-EXEC-001`)
9. **Output handling** — capture, the limit, and **truncation reported explicitly rather than silently** (`THR-22`)
10. **Termination** — signal escalation, the grace period, and how the **complete process group or platform-equivalent job object** is reached (`ARCH-EXEC-002`, `THR-23`)
11. **Audit redaction** — what must never reach a record, and **what redaction cannot do** (`ARCH-OBS-001`)
12. **What a limit breach becomes** — expressed as `ADR-0006` § 1's states rather than as new ones
13. **A table of the excluded forms**, each by what it is, what requesting it produces, and which threat it closes

Enumerable content is carried as **tables**, so the acceptance cases read
structure rather than prose.

### 5.3 Demonstrated failing, and what these cases cannot detect

Every case is demonstrated failing before acceptance, with the `DL-7`
assertions applied to each planting — the anchor unique, the document changed,

naming the case. P06's evidence records two plantings that stopped creating
their defects when the design changed under them; both were caught by the
assertions rather than by review.

| Case | Cannot detect | Found instead by |
|---|---|---|
| `AC-1` | Whether an exclusion is **enforceable**, as opposed to declared | Review; C07's executor; C14's adversarial suite |
| `AC-2` | Whether the default is *implemented* as deny | C07; C14 |
| `AC-3` | Whether a limit's **value** is right | C15's soak; C16's pilot |
| `AC-4` | Whether the escalation actually reaches every descendant on a real kernel | C07 and C09, VM-gated per `TESTING.md` |
| `AC-5` | Whether truncation is reported **legibly** | C11's operator UX |
| `AC-6` | Whether the expression **closes** the threat | Review; the security reviewer of § 8 |
| `AC-7` | Whether the privilege chosen is the **right** one — the case checks that it is decided and its consequence stated, not that the answer is safe | The maintainer, at approval; `RSK-9`'s owner |
| `AC-8` | Whether the mapping is **correct** for every breach | C07; C14's fault matrix |

## 8. Security reviewer

**Codex, named here rather than at approval.**

Program rule 6 separates security-sensitive work from its acceptance review.
P07's security content is the **blast radius of a legitimate command**. Every
control before it decides who may send work and what the work looks like in
flight; this one decides what that work can touch once it is a process, and
`ACT-9` — the malicious command author with legitimate authority — is the actor
it exists to bound.

The remit is § 5.3's column, and `AC-7`'s answer above all: whether the privilege
the ADR chooses is defensible, given that `RFC 0003` admits a caller-selected
user and the agent must therefore hold the authority to **become** other
accounts — including root.

The harvest is the second remit. Profile scripts are host code the agent causes
to run, and the environment they produce is where a deployment keeps
credentials: whether the ADR's bounds on it are sufficient, and whether its
redaction actually keeps that environment out of the audit record, is a semantic
judgement no case here reaches.

`DL-8` applies to how P07 acts on every finding. **Follow the steps in the ledger
entry itself, not a summary here** — including the third tier, for a fix that
changes a *conclusion* rather than an identifier. `G18` is the recent cautionary
case: four rounds, and every finding was a statement of the new semantics left
standing somewhere the previous fix had not reached.

## 11. Decisions requiring confirmation at P07 approval

### `D-P07-1` — P07 may narrow the boundary and may not widen it

Charter § 6 freezes the excluded forms and says so directly: *P07 inherits this
boundary as amended and may narrow it; it may not widen it.* Widening requires an
amendment to RFC 0001 — **not a roadmap entry, not an ADR decision**.

`RFC 0003` is that amendment, made once and deliberately: a caller-selected
execution user, and a shell **only** for the login-environment harvest. P07
inherits the list as it now stands. That the boundary moved once is not licence
for it to move again inside an ADR.

This is recorded as a decision rather than assumed because the temptation is
specific and predictable. An ADR designing real execution meets cases where one
excluded form would be convenient: a working directory for a build, an
environment variable for a proxy, a shell for a pipeline an operator already
has. Each is a widening. **`AC-1` reads the forms out of the charter**, so an
ADR that quietly drops one fails rather than being caught by a reader who
remembers the list.

Narrowing is permitted and should be used where it is honest: if P07 concludes
that something the charter allows is unsafe, excluding it is within scope and
the ADR says so.

### `D-P07-2` — what the agent runs as is decided here, and nothing has decided it yet

`RFC 0003` admits a caller-selected user, so a command runs **as whatever
account it names**, defaulting to one the deployment configures. Nothing decides
what the **agent** runs as, and it must be able to become those accounts.
`ADR-0003` decides the agent's NATS identity and key material and is silent on
its operating-system privilege.

That makes this P07's, and it is the single decision in this task with the
largest consequence: **the agent's privilege is the blast radius of every command
and of `RSK-9`.** An agent running as root can do anything on the host, which is
what a day-2 operations product is usually asked for and also what makes host
compromise total. An agent running as a dedicated unprivileged service account
bounds the damage and cannot perform much of the work the charter's § 2 problems
describe.

The options and their consequences are P07's to lay out; **the choice is the
maintainer's, at approval**, because it is a product decision wearing a
technical costume. `AC-7` checks only that the ADR decides and states the
consequence, not that the answer is right — no case can do that.

### `D-P07-3` — a defect in `ADR-0005` or `ADR-0006` is raised, not fixed

P07 depends on both for the argv payload shape and for what a limit breach
becomes. The rule does not bend: a defect is raised as a finding and the ADR
records it as raised, which is what `ADR-0005` did for the service public halves
and what produced `G15`.

### `D-P07-4` — P07 specifies execution, it does not implement it

No code, no executor, no signal handling. C07 is the task that makes this ADR
true. `G12` and `G13` are why this is written down: both existed because a
P-stage task was asked for artifacts no build existed to produce.
