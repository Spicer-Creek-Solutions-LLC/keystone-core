### 5.2 Document acceptance cases

These replace the feature table for a documentation task. Each states how it
fails, because a case with no failure mode is not a case.

| ID | Claim | Fails when |
|---|---|---|
| `AC-1` | Each of the seven journeys has an exact argv line, an exact exit code, and a named externally observable effect | Any journey lacks any of the three |
| `AC-2` | Every cited `ARCH-*` identifier resolves in `ARCHITECTURE-INVARIANTS.md`, and every journey cites at least one | An identifier does not resolve, or a journey cites none |
| `AC-3` | The excluded-form list covers all nine forms in RFC 0001 § Implementation governance | Fewer than nine appear, or one is stated more permissively than RFC 0001 states it |
| `AC-4` | Every non-goal resolves to a `FUTURE-CAPABILITIES.md` entry or an explicit `Not Planned` bucket in `ROADMAP.md` | A non-goal resolves to neither |
| `AC-5` | Every success measure has a number, a measurement method, and an owner | Any measure is missing any of the three |
| `AC-6` | The validation plan states partner count (≥3), duration, what counts as sustained real-fleet use, what counts as willingness-to-pay evidence, and the narrow/stop branch | Any of the five is absent, or any disagrees with `REBOOT-EXECUTION-PLAN.md` § C16 or `VERSIONING.md` |
| `AC-7` | No capability catalogued in `FUTURE-CAPABILITIES.md` is asserted as in-scope for `v0.6.0` | Any such assertion appears |

The nine forms `AC-3` counts, from RFC 0001: no shell, no stdin streaming, no
scripts, no pipelines, no caller-selected user, no caller-provided environment,
no arbitrary working directory, no batch fan-out, no interactive session.

`AC-1` through `AC-7` are checked by review, not by a script. P00 adds no gate.
Making any of them mechanical is a P11 decision, when a Generation 2 toolchain
exists to host it.

### 5.3 Every case is demonstrated failing before it is accepted

For each of `AC-1` to `AC-7`, P00 produces a variant of the charter that
violates exactly that case, records the check reporting the failure, restores
the document, and records it passing. The evidence lands in the same PR as
`docs/dossiers/P00-acceptance-evidence.md`.

The evidence records which cases fired for each planted defect. A case that
fires on every defect is not discriminating and must be tightened before it is
accepted.

This is R10's countermeasure. Four defects in the transition shared one shape —
a check that could not fail, mistaken for evidence — and an acceptance case
that cannot fail is that same defect in charter clothing. The precedent is
R10 decision 8, which proved a link-gate fix with a planted defect and a
control after R09 had shipped an untested one.

**Scope: P00 only.** Requiring this of every dossier is an amendment to
`REBOOT-EXECUTION-PLAN.md` § "Required task dossier" and needs its own
approval. See `D-P00-2`.

## 6. Validation commands

```
make check
```

That is `docs-lint`, `docs-links` and `capability-catalog-check`
(`Makefile:60`). What it actually covers, verified rather than assumed:

- `docs-links` enumerates from `git ls-files '*.md'` (`Makefile:42`), so a new
  file is checked **only once tracked**. `git add` before validating, or the
  gate passes by not looking.
- `docs-lint` uses `**/*.md` with `gitignore: true`, so it descends into
  dot-directories and skips untracked scratch files.
- The two lists differ by exactly one file, `CLAUDE.md`, which is excluded from
  lint because its `@AGENTS.md` import would break under `MD041`.
- `capability-catalog-check` reads Generation 1 sources at the commit recorded
  in `docs/transition/manifest.json` and needs full history.

Neither gate checks link fragments; `C-05` is open and one fragment is already
broken. P00 does not inherit that finding but must not add to it.

## 11. Decisions requiring confirmation at P00 approval

### `D-P00-1` — the charter supersedes and removes `PROBLEM-STATEMENT.md`

`docs/project/PROBLEM-STATEMENT.md` is a Generation 1 document. It describes
Generation 1's v1.0 — roughly forty state modules, three-node HA clustering,
SPIFFE, Vault, GitOps webhooks, Starlark — and cites `FEATURES.md`,
`PROJECT-DETAILS.md` and `DESIGN.md`, all three of which are absent from the
tree. It is cited as "why this project exists" in `AGENTS.md` § 7 and linked
from `docs/project/README.md` and `PROJECT-REBOOT-REVIEW.md`. **R10 never
audited it**, which is why it is not among the open `D-15`/`D-16`/`D-19`
staleness findings.

P00 defines target operator, problems and non-goals. That is the same question,
answered for Generation 2.

Alternatives considered:

- *Rewrite it for Generation 2.* Rejected: two documents answering "why does
  this exist" is how the drift this reboot exists to correct begins.
- *Retain it and file a separate finding.* Rejected: it leaves a Generation 1
  scope document as the cited authority while the charter states a contradicting
  scope.

The link in `PROJECT-REBOOT-REVIEW.md` is repointed to the archive
(`git show archive-2026-09-pre-v0.6-reboot:docs/project/PROBLEM-STATEMENT.md`),
matching how `AGENTS.md` § 7 already cites Generation 1 research. That document
is R00's historical assessment and its reference is preserved rather than
rewritten. Left unrepointed, `make docs-links` fails.
