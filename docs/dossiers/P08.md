# Dossier — P08, Persistence and audit ADR

The task that decides what survives, where it lives, and whether an operator can
believe it later. Every ADR before it has deferred the record's schema here —
`ADR-0003` for enrollment, `ADR-0005` for which envelope fields may be retained,
`ADR-0006` for every lifecycle transition, `ADR-0007` for what execution must
never emit. P08 is where those deferrals land.

This dossier is a boundary, not an approval. Landing it authorizes nothing: P08
still needs its own presented plan and explicit approval. P08 is a planning and
ADR task and may use one pull request; it does not split into `-A` and `-I`.
Program rule 6's separation of implementation from acceptance review is met by
the independent reviewer named in § 8.

## 3. Exact outputs

One ADR, `docs/adr/0008-persistence-and-audit.md`, containing:

1. **Two stores, server and agent**, each with its own schema and its own API — and why they are not one (`D-P08-2`)
2. **The server schema** — what it holds for agents, enrollment, jobs, results and audit
3. **The agent ledger** — what `ADR-0006` § 3's ordering obligations require it to hold, and nothing beyond

8. **Result storage and output truncation** — where captured output lives, and how `ADR-0007` § 9's truncation is recorded
9. **Append-oriented audit** — what an audit record contains, that it is appended rather than updated, and what that does and does not prove
10. **Sensitive-data handling** — `ADR-0005` § 8's headers, `ADR-0007` § 11's limits, and what must never be written at all
11. **Backup and corruption response** — what a damaged store does, and what an operator is told

## 11. Decisions requiring confirmation at P08 approval

### `D-P08-1` — three risks expire here, and the expectation is that all three renew

`RSK-1`, `RSK-4` and `RSK-9` all name P08. The reasoning is recorded now so a P08
agent neither resolves them because the expiry arrived nor renews them without
noticing what P08 does change.

**They form a circle.** `RSK-1`'s control says every issued command is audited
*"though a party holding both keys can also rewrite that audit"*. `RSK-4`'s says
agent-side ledgers permit a forensic reconstruction *"but the operator reaches
those ledgers only through the server"*. `RSK-9`'s says the agent *"owns its own
ledger"*. Each leans on a record that one of the others controls.

**A schema does not break that circle.** What would is a record that a
compromised party cannot silently rewrite — tamper-evidence, and specifically
tamper-evidence anchored outside the deployment, since a hash chain the server
holds is a hash chain the server can rebuild. That is `D-P08-3`.

So the expectation is renewal with sharper reasoning, exactly as `ADR-0006` and
`ADR-0007` renewed `RSK-9`. **If the maintainer reads any of the three as
resolvable at P08, that changes the ADR's scope materially** and is a decision
for approval rather than review.

### `D-P08-2` — two stores, and no abstraction over them

The execution plan says it directly: *do not introduce a shared mega-store
interface.* The server and the agent store different things for different reasons
— the server holds fleet state and the audit; the agent holds one host's ledger —
and the only thing they have in common is being SQLite.

An interface over both would make that coincidence look like a design, and every
later change would have to be expressed in terms of it. `AC-2` checks the
separation; it cannot check that a helper introduced at C02 is not the same thing
by another name, which is why § 10 hands P11 the question of whether a lint can.

### `D-P08-3` — tamper-evidence is deferred, and the deferral needs a trigger

The plan lists Postgres and tamper-evidence as *future decision points*. Deferring
is right for `v0.6.0`: tamper-evidence that means anything needs an anchor outside
the deployment, which is a new dependency and a new operational burden for a
release whose promise is one narrow journey.

**But a deferral without a trigger is an omission with better manners.** `AC-11`
requires each deferred point to name what would cause it to be taken up, and for
tamper-evidence the honest trigger is whichever comes first: an external operator
asking whether the audit can be trusted against the server that produced it, or
`RSK-1`/`RSK-4` reaching an expiry with no other mitigation available.

The ADR must also say plainly what append-oriented storage does **not** prove, so
that nobody later reads "append-only" as the tamper-evidence it is not.

### `D-P08-4` — a defect in an earlier ADR is raised, not fixed

P08 depends on four accepted ADRs. A defect is raised as a finding and recorded
as raised — `ADR-0005` did that for the service public halves and produced `G15`;
`ADR-0007` did it twice and one of those is still open.

**`ADR-0007` § 13 raised that `ADR-0006` has no lifecycle state for a
resource-limit kill.** P08 stores whatever state that becomes, so it will meet
the gap. It does not close it: that is `ADR-0006`'s, and P08 records the
encounter rather than inventing a state to store.

### `D-P08-5` — P08 specifies the store, it does not implement it

No migrations, no SQL, no file layout beyond ownership and mode. C02 is the task
that makes this ADR true. `G12` and `G13` are why this is written down: both
existed because a P-stage task was asked for artifacts no build existed to
produce.
