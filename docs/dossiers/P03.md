# Dossier — P03, Enrollment and identity ADR

The task that decides how an agent acquires an identity it did not have. It is
the only key transition Generation 2 specifies, and `THREAT-MODEL.md` § 8 says
so plainly: everything after enrollment is undesigned.

This dossier is a boundary, not an approval. Landing it authorizes nothing: P03
still needs its own presented plan and explicit approval. P03 is a planning and
ADR task and may use one pull request; it does not split into `-A` and `-I`.
Program rule 6's separation of implementation from acceptance review is met by
the independent reviewer named in § 8.

## 3. Exact outputs

One ADR, `docs/adr/0003-enrollment-and-identity.md`, containing:

1. **Token creation** — who issues a one-use token, what it is scoped to, and what the server records when it does
2. **Token handling** — the charter defers three questions to P03 and each must be answered: whether the token is also accepted on standard input, the required file mode, and the file's lifetime. `--token-file` itself is fixed by P00 and is not reopened
3. **The bootstrap credential** — token-scoped, one-use, short expiry, and the account it lives in (`ADR-0002` § 1)
4. **Token-specific subjects** — named by role, never as literal strings; the grammar is P04's
5. **Agent-generated keys** — the agent's NATS identity key, envelope-signing key and payload-decryption key are **generated on the agent**, so the server never holds `AST-4` or `AST-5`. `ARCH-NATS-006` requires them separate and forbids reusing an NKey seed as a Keystone key
6. **Server validation** — what the server checks before issuing, and what it does with a token that is spent, expired or unknown (charter § 5.1 fixes the exit codes)
7. **Permanent credential issuance** — using the account signing key of `ADR-0002` § 2
8. **The staged protocol, in order**, as `ARCH-NATS-004` requires: issue pending credentials; fsync and atomically rename the agent credential file at mode `0600`; prove a permanent connection; mark the identity active; revoke bootstrap access; **verify the revocation**
9. **A crash-recovery path for every stage boundary** — `ARCH-NATS-004` requires one per stage, and `THR-04` is the threat it answers
10. **Bootstrap expiry** as the failure backstop, with its relationship to the recovery paths
11. **Reconnect** — what an enrolled agent does when its connection drops, and what it must not re-do
12. **Re-enrollment** — when an identity is replaced rather than recovered, and what happens to the old one
13. **Rotation of agent-side material** — `AST-3`, `AST-4`, `AST-5`. P03 also decides where `AST-16`, the Keystone account signing key, lands in the split: rotating it invalidates every identity it signed, which is a fleet-wide re-enrollment and therefore arguably P03's, but the dossier requires it *accounted for* rather than assigning it in advance
14. **Clock assumptions** — expiry and JWT validity depend on time; state what is assumed about skew between server, broker and agent, and what breaks if it is wrong
15. **Disaster recovery** — the fleet's identities after the server's store is lost
16. **Publish-acknowledgement inboxes** for any principal P03 introduces that publishes to a stream (`ADR-0002` § 8)

Enumerable content is carried as **tables**, so the acceptance cases read
structure rather than prose — `DL-2`'s countermeasure applied before the fact.

### 5.2 Document acceptance cases

| ID | Claim | Fails when |
|---|---|---|
| `AC-1` | Every stage `ARCH-NATS-004` names appears, in the order the invariant gives, and each names a crash-recovery path | A stage is absent, out of order, or has no recovery path |
| `AC-2` | The agent's identity, signing and decryption keys are stated to be generated **on the agent**, and no output describes any of the three reaching the server | A key is server-generated, or transits to the server |
| `AC-3` | Revocation of bootstrap access is **verified**, not merely performed, and the verification is a distinct step | Revocation is stated with no verification step |
| `AC-4` | Every threat P01 assigns to journey 5.1 — `THR-01` to `THR-05` — is answered by a named mechanism in this ADR | A 5.1 threat has no answer |
| `AC-5` | The charter's three deferred token-handling questions — standard input, file mode, file lifetime — are each decided | Any of the three is left unstated |
| `AC-6` | `RSK-7` is **split**, and **every asset that cited it lands in exactly one part** — `AST-3`, `AST-4`, `AST-5`, `AST-6`, `AST-7`, `AST-8`, `AST-16`. Each part carries owner, rationale, compensating control and a dated expiry. No § 8 row, no § 8 prose, and no other risk's compensating control still cites a risk identifier the split has replaced | `RSK-7` is left whole; an asset that cited it appears in no part or in more than one; a part has no owner; or any row still points at a replaced identifier |
| `AC-7` | Clock assumptions are stated, with what breaks if skew exceeds them | Expiry or JWT validity is specified with no stated time assumption |
| `AC-8` | No literal Keystone subject string appears, except in an example explicitly marked as P04's to fix | A literal subject appears unmarked |

`AC-6` exists because `RSK-7` names P03 as its expiry while covering material
P03 does not own. A single risk that two tasks each half-own is how one half
gets forgotten, so the dossier requires the split rather than permitting a
renewal that quietly carries the service keys forward.

**It enumerates the assets rather than the parts**, and that is the correction
this dossier needed. An earlier version defined the split as "agent-side plus
service-key", which silently omitted `AST-16` — the account signing key `G10`
had added to the threat model days earlier, pointing at `RSK-7` like everything
else. A case that names the halves can be satisfied while an asset falls between
them; a case that names the assets cannot. **Seven rows in § 8 cite `RSK-7`, and
so does `RSK-1`'s compensating control**, which is why § 2 widens the allowed
paths to reach them: a split that leaves seven stale pointers behind has moved
the inconsistency rather than removed it.

### 5.3 Demonstrated failing, and what these cases cannot detect

Every case is demonstrated failing before acceptance, with the `DL-7`
assertions applied to each planting: the anchor is unique, the document
changed, the mutated document **actually carries the defect** verified by
parsing it directly, and the reported failure names the case. Evidence lands as
`docs/dossiers/P03-acceptance-evidence.md`.

**These cases were written from the enrollment happy path, and that is where
they will be wrong.** P02 learned this twice in one task: `AC-4` was derived
from the pull-consumer case and had to be widened by `G08` when acknowledgement
subjects turned out to carry unenumerable tokens, then again by `G09` when a
publisher's inbox turned out to have no consumer at all. Both were satisfiable
rules written from one example of a thing. P03's equivalent exposure is the
**crash-recovery and re-enrollment paths**: a case phrased around "the agent
enrolls" will not hold when the agent enrolls twice, or half-enrols and dies.

| Case | Cannot detect | Found instead by |
|---|---|---|
| `AC-1` | Whether a recovery path is **correct**, or merely present. A path that resumes into an inconsistent state satisfies this exactly as well as one that does not | Review; C05, where the crash matrix is executed |
| `AC-2` | Whether an implementation honours it. The ADR can say "generated on the agent" and C01 can still generate server-side | C03 and C05, and `ARCH-TEST-002`'s negative identity tests |
| `AC-3` | Whether the verification **proves** revocation, as opposed to observing something consistent with it | Review; C03's negative matrix, where a revoked credential must fail to connect |
| `AC-4` | Whether the named mechanism actually mitigates the threat, which is the limit every P01 case carried | Review; C14's adversarial suite |
| `AC-5` | Whether the decisions are **good** — a stated file lifetime of a year passes | Review; the maintainer, who owns the resulting risk |
| `AC-6` | Whether the split is drawn in the right place, whether the service-key part is genuinely P05's, and whether `AST-16` is owned by the task that can actually rotate it | Review; P05, when it inherits a risk it cannot discharge either |
| `AC-7` | Whether the stated skew assumption is **realistic** for the deployments the charter contemplates | Review; C05 and C14 |
| `AC-8` | Whether a role-named subject is describable in the grammar P04 will choose | P04, when a required role has no representable subject |

## 8. Security reviewer

**Codex, named here rather than at approval.**

Program rule 6 separates security-sensitive work from its acceptance review.
P03 decides how identity is established — the second of RFC 0001's six
cumulative security layers — and a defect in it is a defect in every identity
the fleet ever holds. The drafting agent cannot review it.

The remit is the semantic properties in § 5.3: whether a recovery path resumes
into a consistent state, whether the revocation verification proves anything,
and whether `RSK-7`'s split is drawn where the material actually divides.

`DL-8` applies to how P03 acts on every finding. **Follow the steps in the
ledger entry itself, not a summary of them here** — the entry stands at `Failed`
and has been revised twice, and a restatement in this dossier would drift from
it the next time it changes.

## 9. Rollback

One PR, documentation only. No runtime state, no forge mutation, no remote
apply. Rollback is reverting the merge commit; RFC 0001 commits to continuous
history, so it is a revert and never a rewrite.

The `THREAT-MODEL.md` edits revert with it, returning `RSK-7` to its undivided
form and § 8's rows to citing it. That is correct: the split is a consequence of
P03's decisions, and without them the risk stands as one.

### `D-P03-3` — P03 decides the protocol, it does not implement it

No code, no credential files, no JWT fixtures, no test vectors. Those are C01
and C03. An ADR that ships a working enrollment has ratified an implementation
rather than decided a design, which RFC 0001 forbids.

P03 is the first task to build on an accepted ADR. If `ADR-0002` proves wrong
where P03 touches it, P03 records the finding and stops.
