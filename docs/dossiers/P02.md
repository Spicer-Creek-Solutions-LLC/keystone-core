# Dossier — P02, NATS-native capability ADR

The first Generation 2 ADR, and the first messaging ADR, which makes it the
first real test of `ARCH-NATS-008`. It decides how Keystone uses NATS: accounts,
identities, subjects, permissions, JetStream shapes, limits and deployment
modes — inside constraints RFC 0001 already fixed, and against the threats P01
already modelled.

This dossier is a boundary, not an approval. Landing it authorizes nothing:
P02 still needs its own presented plan and explicit approval.

P02 is a planning and ADR task and may use one pull request; it does not split
into `-A` and `-I`. Program rule 6's separation of implementation from
acceptance review is met by the independent reviewer named in § 8.

## 3. Exact outputs

One ADR, `docs/adr/0002-nats-native-capabilities.md`, containing:

1. **Accounts** — the dedicated Keystone account and the separate system account (`ARCH-NATS-001`), and what each holds
2. **Operator and JWT trust** — the trust chain, who signs what, and where the operator seed lives relative to the deployment
3. **Principals** — the command publisher, enrollment service, result consumer, presence consumer, monitoring role and every agent, as distinct identities, co-located or not (`ARCH-NATS-002`)
4. **Subject roles** — for each principal, the *direction and scope* it requires: which role publishes, which subscribes, and whether the scope is one agent or the deployment. Subjects are named by role ("the agent's own command subject"), never as literal strings — the canonical grammar is P04's (§ 12)
5. **What P04 writes its matrix against** — the principal list of item 3 and the consumer shapes of item 7, stated so that a principal-by-subject permission matrix can be derived from them without reopening P02
6. **The response-permissions decision** — `Adopt`, `Evaluate`, `Defer` or `Reject`, decided rather than left unstated (`D-P02-4`)
7. **JetStream streams and durable consumers** — their shapes, subjects, retention and acknowledgement policy, with `MaxAckPending` and `FilterSubject` as `ARCH-NATS-009` requires, and finite `MaxDeliver` with explicit `BackOff` as `ARCH-NATS-010` requires
8. **The exact data-plane `$JS.API` and reply allowlist** — enumerated literally. `ARCH-NATS-005` names `P02/P04` jointly: P02 produces the enumeration, P04 tests it against generated production JWTs (§ 4)
9. **Limits** — connection, subscription, payload, consumer, byte, age and message, per account and per stream, with no unbounded stream or consumer (`ARCH-NATS-007`)
10. **Advisories** — which are consumed, by which principal, in which account
11. **Headers** — including `Nats-Msg-Id` and what deduplication it does and does not provide
12. **TLS** — where it terminates, and an explicit statement that it is not end-to-end payload secrecy (RFC 0001)
13. **Credential rotation** — the broker-side mechanism, and what it does *not* reach. P01's § 8 records that revoking a NATS identity does not revoke a Keystone signing or decryption key
14. **Deployment modes** — including the isolated-network case `ARCH-COMM-002` requires, where server and agents share only the broker
15. **The `Adopt` / `Evaluate` / `Defer` / `Reject` matrix**, one row per relevant NATS capability, each with evidence (`ARCH-NATS-008`)

The ADR carries these as **tables** wherever the content is enumerable — the
capability matrix, the principal list with its direction and scope, the
allowlist, the limits. That is `DL-2`'s
countermeasure applied before the fact: P01 demonstrated that checks reading
structure catch what checks reading prose cannot, and P02's acceptance cases
depend on it.

RFC 0001 § "NATS-first architecture" closes with a constraint this task must
satisfy and an implementation task is most likely to violate, so it is repeated
here rather than cited:

> P02-P06 decide the safe configuration and protocol details inside these
> constraints; they do not merely ratify an implementation selected in advance.

### 5.2 Document acceptance cases

| ID | Claim | Fails when |
|---|---|---|
| `AC-1` | Every capability in RFC 0001's **required initial set** appears in the matrix with exactly one verdict | A required capability is absent, or carries no verdict, or carries more than one |
| `AC-2` | Every capability in RFC 0001's **deferred set** — response permissions, KV, subject mappings, Object Store, queue groups, leaf nodes, superclusters — carries `Defer` or `Reject`, or an `Adopt` naming the demonstrated need | A deferred capability is silently adopted, or absent from the matrix entirely |
| `AC-3` | Every matrix row carries evidence, and the evidence is not a restatement of the verdict | A row has an empty evidence cell, or one that merely repeats the verdict word |
| `AC-4` | The data-plane `$JS.API` and reply allowlist is enumerated literally | Any allowlist entry contains `>` or `*`, or an administrative `$JS.API` subject appears as permitted |
| `AC-5` | Every principal `ARCH-NATS-002` requires is named, with the direction and scope it needs | A required principal is missing, or one is named with no direction or no scope |
| `AC-6` | Every `ARCH-NATS-*` invariant maps to a section that satisfies it or explicitly registers it, naming the owning task | An invariant maps to nothing, or is registered with no owner named |
| `AC-7` | `RSK-2`, `RSK-3` and `RSK-10` are each resolved or renewed, with a dated expiry and a stated reason | Any of the three is left with its original expiry and no decision recorded |
| `AC-8` | No literal Keystone subject string appears in the ADR, except in an example explicitly marked as P04's to fix | A literal subject appears unmarked, which is P02 deciding a grammar that belongs to P04 |

`AC-3` exists because the `Adopt` column is where a vague token hides. A verdict
without evidence satisfies `ARCH-NATS-008`'s letter and defeats its purpose, and
an evidence cell reading "adopted because it is the native mechanism" is the
same defect one sentence longer.

`AC-7` exists because a residual risk whose expiry names a task, and which that
task then does not mention, expires by silence. P01 wrote the expiry as
"2027-03-13, or P02, whichever is sooner" precisely so this could be checked.

### 5.3 Demonstrated failing, and what these cases cannot detect

Every case is demonstrated failing before acceptance, per
`REBOOT-EXECUTION-PLAN.md` § "Required task dossier", with the `DL-7`
assertions applied to each planting: the anchor is unique, the document changed,
the mutated document *actually carries the defect* verified by parsing it
directly, and the reported failure names the case under demonstration. Evidence
lands as `docs/dossiers/P02-acceptance-evidence.md`.

**These cases are structural and will miss semantic defects.** P01's record is
the reason this is stated as an output rather than learned: eleven findings over
three review rounds, every one falling under a limits row written before round
one, and not one caught by a case.

| Case | Cannot detect | Found instead by |
|---|---|---|
| `AC-1` | Whether a capability *absent from RFC 0001's list* is relevant and missing — the list is a floor, not a census | Independent review; C03 when a needed capability has no decision to implement |
| `AC-2` | Whether a `Defer` is honest, or is an `Adopt` the author did not want to argue for | Independent review; the deferred set is the reviewer's primary target |
| `AC-3` | Whether the evidence is *true*, or supports the verdict it sits beside | Independent review against the NATS documentation the row cites |
| `AC-4` | Whether the enumerated allowlist is *sufficient* for the consumer it serves, or *minimal* | C03's negative identity matrix, where an insufficient allowlist fails to connect and an excessive one fails a denial test |
| `AC-5` | Whether the direction and scope named for a principal are the *right* authority for it | Independent review; P04's generated JWTs and negative tests (`ARCH-TEST-002`) |
| `AC-6` | Whether the section that claims to satisfy an invariant actually does. A shallow section satisfies the map as well as a deep one | Independent review — the same limit `AC-6` carried in P01, restated because the shape is identical |
| `AC-7` | Whether a renewal is *justified* or merely restated with a later date | The maintainer, who owns each risk by name |
| `AC-8` | Whether a role-named subject is *describable* in the grammar P04 will choose. P02 can leave P04 an impossible shape and this case will not notice | P04, when a required role has no representable subject |

Every row says review or a later task, which is the point: § 8 names a reviewer,
and a green acceptance suite does not discharge them.

## 8. Security reviewer

**Codex, named here rather than at approval.**

Program rule 6 separates security-sensitive work from its acceptance review.
P02 decides the authorization boundary for the whole product — accounts,
identities, subject permissions and the `$JS.API` allowlist are four of RFC
0001's six cumulative security layers — so the drafting agent cannot review it.
The remit is the semantic properties in § 5.3, and in particular whether each
`Defer` is honest and each evidence cell supports its verdict.

**`DL-8` applies to how P02 acts on that review, and P02 is the first task that
can exercise its current countermeasure.** The entry stands at `Failed` and has
been revised twice, the first revision having failed before the second was
written.

**Follow the steps in the ledger entry itself, not a summary of them here.**
This dossier deliberately does not restate them: a restatement in a second
document is what `G04` was correcting, and a countermeasure that is revised as
often as this one will outrun any paraphrase.

The outcome on this task's evidence is `Held` if the steps catch a recurrence or
`Adopted` if the class had its chance and did not appear. Either is a separate
ledger edit and not P02's to make unilaterally.

## 9. Rollback

One PR, documentation only. No runtime state, no forge mutation, no remote
apply. Rollback is reverting the merge commit; RFC 0001 commits to continuous
history, so it is a revert and never a rewrite.

The `THREAT-MODEL.md` § 9 edits revert with it, returning `RSK-2`, `RSK-3` and
`RSK-10` to their original expiries. That is the correct behaviour: the risks
were discharged *by* P02's decisions, and without those decisions they stand.

## 11. Decisions requiring confirmation at P02 approval

### `D-P02-1` — the ADR is `0002`

Next sequential per `docs/adr/README.md`. `0000` and `0001` are templates, which
that index lists as accepted ADRs dated `2024-01-01` — a Generation 1 artifact,
since a template is not a decision. P02 takes `0002` and leaves the wrinkle
alone; correcting the index is a control-document task (§ 12).

### `D-P02-2` — P02 may edit `THREAT-MODEL.md` § 9, and nothing else in it

`RSK-2`, `RSK-3` and `RSK-10` expire on P02. Discharging them requires editing
their rows, and the alternative — a follow-up task — is how a risk expires by
silence. The permission is three rows wide and is stated in § 2 as such.

### `D-P02-3` — P02 decides configuration, it does not generate it

No NATS configuration files, no JWTs, no fixtures, no Docker matrix. Those are
P04 and C03. An ADR that ships a working configuration has ratified an
implementation rather than decided a design, which RFC 0001 forbids in the
sentence quoted in § 3.

### `D-P02-4` — the response-permissions decision is made, not deferred by omission

RFC 0001 lists response permissions among the capabilities introduced "only by a
later accepted ADR and demonstrated need", and the execution plan names the
decision explicitly in P02's paragraph. `Defer` is an acceptable verdict with
evidence; silence is not a verdict.
