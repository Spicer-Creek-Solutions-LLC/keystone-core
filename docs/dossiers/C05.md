# Dossier — C05, one-use enrollment vertical slice

The fifth Stage C task, and the first with a journey.

C01 built the envelope, C02 the stores, C03 the authorization a broker enforces,
C04 the socket an operator crosses. None of them has run a journey. C05 runs
the charter's § 5.1 end to end: an operator creates a token through the public
CLI, an agent redeems it over NATS, and the agent ends holding a permanent
identity with its bootstrap access revoked **and the revocation verified**.

**It is blocked before it starts, by three gaps in accepted documents.** § 11
marks each one *blocking*, and none is C05's to close:

- **Who revokes (`D-C05-1`).** `ADR-0003` § 6 has the server revoke the
  bootstrap identity at S5, and `ADR-0002` § 13 says the server can do that
  *"with its account signing key"*. Measured against the broker this project
  pins, **it cannot**: a revocation is a change to the account JWT, the broker
  trusts only an operator-signed account JWT, and the operator seed is held
  outside every Keystone process by `ADR-0002` § 2.
- **TLS (`D-C05-8`).** `ADR-0002` § 12 requires TLS on every connection, no
  task implements it, and C05 lands the first production NATS connections.
- **The token secret (`D-C05-9`).** `ADR-0003` § 1 generates a secret that
  § 5's validation never checks. Presenting it would put confidential material
  on the enrollment path, which § 4 says carries none.

**Proposed: one prerequisite task settles all three before C05 is approved.**
All three are the same boundary: what `ADR-0003`'s protocol needs from
`ADR-0002`'s broker. Two of them change the generated broker configuration.

This dossier is a boundary, not an approval. Landing it authorizes nothing: C05
still needs its own presented plan and explicit approval, and it is a
**behaviour workstream**, so it splits into `C05-A` and `C05-I` with different
agents per [`REBOOT-EXECUTION-PLAN.md`](../project/REBOOT-EXECUTION-PLAN.md)
§ "Required task dossier". Roles alternate from C04: **`C05-A` is Codex's to
write and Claude's to review**, and `C05-I` the reverse.

### 5.3 Demonstrated failing, and what these cases cannot detect

Every case is demonstrated against a planted defect before it is trusted, per
`DL-1`, with one mutation per case and its failure set recorded. C04 set two
standards here, and C05 inherits both:

- **A throwaway reference implementation with a mutation matrix**, run by
  `C05-A` before freezing, shows the contract is satisfiable and each case
  discriminates.
- **The matrix must plant the defect review would name.** C04-A's first matrix
  never planted *hold, read, decide*, and review found it. For C05, the
  defects most worth planting are the ones `D-C05-1` measured:
  - a revocation signed with the account signing key, which the broker answers
    `200 jwt updated` and does not enforce;
  - a verification that re-reads the account and trusts what it reads.

Two traps specific to this task:

- **A revocation case is satisfied by an identity that never worked.** The
  bootstrap must be shown to connect before revocation, or a refusal afterwards
  proves nothing.
- **A crash case is satisfied by a stage that was never reached.** Each kill must
  be shown to have landed at its boundary, by the fault point's audit record,
  before the recovery is judged.

**What these cases cannot detect.**

- **The broker's clock.** `ADR-0003` § 12 assumes server and broker agree within
  a bound, and a container shares its host's clock.
- **Provenance of the bundle.** § 14 concedes this.
- **Durability against power loss.** A killed process's writes survive in the
  page cache; a VM that can be reset is where that is tested.

## 11. Decisions requiring confirmation at C05 approval

### `D-C05-1` — who revokes the bootstrap identity (blocking)

`ADR-0003` § 6 S5 has the server revoke the bootstrap identity, and S6 has it
verify the revocation *"by re-reading the account state"*. `ADR-0002` § 13 says
the server can revoke *"with its account signing key"*. `ADR-0002` § 2 holds the
operator seed outside every Keystone process.

**Measured against `nats:2.15.0-alpine`**, the broker `C03-A` pins, with the
`nats-io/jwt/v2` and `nats.go` this module uses. The configuration was an
operator, a system account, and a Keystone account carrying one signing key.
The server pushed an account JWT listing the bootstrap user as revoked, via
`$SYS.REQ.CLAIMS.UPDATE`.

| Resolver | Account JWT re-signed by | Broker's reply | Revoked bootstrap user | An unrevoked user of the same account |
|---|---|---|---|---|
| `full` (updatable) | **account signing key**, account already loaded | `200 jwt updated`; log: `Update … resulted in error account validation failed` | **still connects** | connects |
| `full` | **account signing key**, account not yet loaded | `200 jwt updated` | refused | **refused: the whole account is unusable** |
| `full` | operator key | `200 jwt updated` | refused | connects |
| `MEMORY` — what C03 generates | either | no responder: runtime updates unsupported | still connects | connects |

**Three findings, each worse than the one before.**

1. **The server's key cannot revoke.** An account JWT must be signed by the
   operator. The signing key ADR-0002 gives the server signs *users*, not the
   account that lists their revocations.
2. **The failure is silent.** The broker answers `200 jwt updated` to an update
   it then refuses to apply, and a re-read of the account returns the stored JWT
   **listing the revocation**. `ADR-0003` § 6's S6, *"re-read the account state
   and confirm the bootstrap identity is listed"*, therefore reports success for
   a revocation that is not in force. **The verification step the invariant
   exists for cannot detect this failure.** It confirms what was stored, not what
   is enforced.
3. **After a broker restart it takes the whole account down.** The stored,
   invalid JWT becomes the one the broker loads, and every Keystone identity is
   refused: every agent and every service principal.

`C03-I`'s `NEG-7` passes because the generator revokes with the operator key at
generation time, in a process outside the deployment. That proves a revoked
identity cannot connect. It does not prove the server can revoke one.

**This is not C05's to decide.** It changes who holds what in `ADR-0002`, and
possibly what `ARCH-NATS-004` requires. Settling it under a C05 approval would
amend an accepted ADR sideways, which `D-C03-4` refused for the same reason.
**Proposed: a G or P task amends `ADR-0002` §§ 2, 12 and 13 and `ADR-0003`
§§ 1, 5 and 6 before C05 is approved**, settling this, `D-C05-8` and `D-C05-9`
together. It chooses among:

| Option | Consequence |
|---|---|
| **The server holds an operator signing key** | S5 and S6 work as written. An operator signing key can sign **any** account, so a compromised server could mint accounts on the operator, widening `RSK-3` from the broker administrator to the server. `ADR-0002` § 2 rejected exactly this for the seed |
| **A revoker outside every Keystone process holds the operator key**, and the server asks it | Custody is unchanged. It adds a component and a trust boundary, and enrollment then depends on a process the product does not run. `ADR-0010`'s topology has no place for it |
| **Bootstrap access ends by expiry and by the server's refusal, not by broker revocation** | No new key. `ARCH-NATS-004` names revocation **and verification**, so this changes an invariant, which is an RFC (`RFC.md`). `THR-03`'s window becomes the token's lifetime, bounded by minutes rather than closed |
| **A separate bootstrap account whose JWT the server may re-sign** | NATS gives no account that authority except through the operator, so this is the first option under another name |

**Whichever is chosen, two things follow and C05 inherits them.**

- **S6's verification must be an observation of the broker refusing the
  bootstrap identity, never a re-read of claims.** The table shows why.
- **The generated configuration needs a resolver that accepts updates at
  runtime.** `MEMORY` accepts none. That is C03's generator output, and § 3.3
  grants the change without granting any change to the matrix.

### `D-C05-2` — where the agent identifier comes from

**Carried from `D-C03-4`, which recorded it so that C05 would not discover it as
a blocker.** `ADR-0004` § 1 requires `<id>` to be *server-assigned, never
operator-supplied*. `ADR-0003` § 1 records only `--agent-name`, which the charter
calls a label. `D-P04-5` required the gap raised and stopped at, and it has not
been resolved.

**Proposed: the server assigns `<id>` at token creation**, from its own random
source, validated by `internal/protocol.ValidIdentifier` and never equal to
`ReservedSender`. The token binds `<id>` and the name together; the name stays a
label; and § 5's *"the enrolling party does not supply one"* holds for both.
This reads as consistent with both ADRs rather than as amending either. It still
decides the origin of the identifier every subject is built on, so it is the
maintainer's to confirm and not C05's to assume.

### `D-C05-3` — how S6 reaches the agent, and what S3's proof is

The charter makes the agent's exit `0` mean *permanent identity active and
bootstrap revoked*. `ADR-0003` § 6 says the agent exits `0` only after S6 *"is
confirmed to it"*. **No principal in `ADR-0004` § 4's matrix can tell it.** After
S3 the agent holds only its permanent identity. That identity subscribes to
`ks.job.<own>.>` and its own inbox; the enrollment service publishes only
`ks.enroll.*.reply`; and the command publisher's `ks.job.*.cmd` is a JetStream
path, which is C06's. The bootstrap connection cannot carry it either: revoking
the user is what ends that connection.

S3 is under-specified in the same way. The agent publishes a proof *"on its own
subject"*, and the enrollment service subscribes to no agent subject. The
presence consumer and the monitoring role do.

| Option | Consequence |
|---|---|
| **The agent verifies S6 itself**: after its permanent connection is proven, it retries the bootstrap connection until the broker refuses it | No matrix change. It uses the observation `D-C05-1` requires anyway. It cannot tell revocation from expiry, which the case list must accept or refuse explicitly |
| **Add a server-to-agent grant for enrollment completion** | A change to `ADR-0004` § 4 and to `C03-A`'s frozen matrix: an amendment with its own review |

**Proposed: the first**, with S3's proof being the agent's first **presence**
envelope (`ADR-0005` § 7), observed through the presence consumer the server
already runs. Presence is signed by `AST-4`, so it also proves control of the
signing key. It is the maintainer's because it reads *"confirmed to it"* as
*"observed by it"*.

### `D-C05-4` — broker endpoints, trust anchors and credentials, for both sides

`ADR-0003` never says how the agent learns where the broker is, and the
charter's footnote leaves *"connection arguments"* to P03, which did not decide
them. **The server has the same gap, and it is larger.** Its configuration today
holds only `[operator]`, `[store]` and `[faults]` (`C04-A`'s frozen interface),
yet C05's enrollment service must connect to the broker as several principals:

- the **enrollment service**, to subscribe to `ks.enroll.*.request` and reply;
- the **presence consumer**, to observe S3's proof (`D-C05-3`);
- whatever `D-C05-1` decides **revokes and verifies**.

**Proposed: each is configuration, and none is bundle content.**

| Binary | Broker address | Broker trust anchor | Credentials |
|---|---|---|---|
| `keystone-server` | configured | configured (`D-C05-8`) | **one configured path per credential C05 consumes**: the enrollment service's `.creds`, the presence consumer's `.creds`, the account signing seed, and whatever revocation material `D-C05-1` settles. **Never a directory** — see below |
| `keystone-agent` | configured | configured (`D-C05-8`) | none before enrollment. The bundle carries the bootstrap credential, and S2 writes the permanent one where the agent's configuration says |

**Explicit paths, not C03's `creds/` directory.** `internal/natsauth/write.go`
writes every generated credential into one directory: all five service
principals, and the generated bootstrap credentials. `ADR-0002` § 3 holds that
*"a single server process holding four service credentials is still four
principals, and a compromise that yields one does not yield the others"*. A
directory the server account can read yields all of them. C05 uses two service
roles. The command publisher, result consumer and monitoring role belong to later
tasks, and the generated bootstrap seeds belong to no running process. Each consumer
therefore gets exactly the credential it uses, by path.

**A credential in the wrong slot is refused, not used.** The server checks that
each configured credential's JWT is the role its slot expects, by the grants the
frozen matrix gives that role, and refuses to start otherwise. That preserves
the broker-enforced boundary against a misconfiguration, and gives § 5.2 a
negative case.

The bundle's integrity is already the whole of the agent's trust in the server
(`THR-51`), and it need not also carry where the broker lives. **C05 freezes
these keys** as C04 froze the operator ones, and adding keys to C04's server
file is an extension that C04's frozen interface permits (*"C04-I may accept
more"*).

### `D-C05-5` — where the contract lives, and how a crash is caused

The register names `test/e2e/docker/enrollment_test.go` and
`test/e2e/docker/journey_test.go` as the evidence for C05's two rows. C03 faced
the same choice and moved its evidence paths into its contract package
(`D-C03-2`).

**Proposed: the same.** The contract lives in `test/contract/enrollment/`, and
both rows name it; § 3.3 grants the register change. **The crash mechanism is
`ADR-0010` § 5's.** Each enrollment boundary gets a fault point in the shipped
agent or server, inert by default and recorded in the audit when enabled, and
the harness kills the process when the fault point is reached. `C04-A`'s `FLT-1`
established the audit half. Timing a `kill` from outside is not a mechanism: it
lands between boundaries as often as on them.

### `D-C05-6` — what C05 owes of *"the agent appears in § 5.2"*

The charter's § 5.1 observable effect ends with *"the agent appears in § 5.2"*.
§ 5.2 is list and presence, which is C10's. **Proposed: C05 records the agent as
`active` in the store and proves that there. The listing is C10's**, and
`C05-I`'s evidence states the clause as owed rather than implying it.

### `D-C05-7` — the first journey verb

`internal/cli/boundary_test.go`'s `TestNoJourneyVerbIsWired` forbids every
journey verb as a literal in non-test source. **Proposed: C05 removes `"enroll"`
from that list and nothing else**, so that `run`, `status`, `output`, `cancel`,
`audit` and `agents` stay forbidden until their own tasks. This is the narrowing
C04-I's review asked of the `net` loosening, applied before it has to be asked.

### `D-C05-8` — TLS on every connection (blocking)

`ADR-0002` § 12 is accepted: *"TLS on every connection, terminating at the
broker."* **No task implements it.** C03's generated broker configuration has
no `tls` block, and the Docker topology runs plaintext. C05 creates the first
production server and agent connections to the broker.

**It cannot be raised and deferred, as an earlier draft of this dossier
proposed.** Landing plaintext production connections knowingly contradicts an
accepted decision, and *"the evidence says so"* does not make that compliant.
Two ways to close it:

| Option | Consequence |
|---|---|
| **A prerequisite task implements it**: the generator emits a CA, a broker certificate and a `tls` block; clients verify against a configured anchor | C05 stays bounded, and C03's generator stays the one source of broker configuration. It is a change to generator output, so C03's broker fixture and topology are re-run against it |
| **C05 implements it** | C05's paths grow by the generator's TLS output, the topology's certificates and every client's verification, on top of the first journey |

**Proposed: the prerequisite task, the same one `D-C05-1` needs.** Both change
the generated broker configuration (a resolver that accepts updates, and a `tls`
block), and settling them together means C03's fixture is re-proven once.

### `D-C05-9` — the token's secret (blocking)

`ADR-0003` § 1 generates *"a high-entropy random identifier and secret"*, and
§ 1 and § 2 treat the token as something the bundle carries in addition to the
bootstrap credential. **§ 5's validation never checks a secret.** It checks, in
order:

1. the token exists;
2. its state admits enrollment;
3. it has not expired;
4. the presenting bootstrap identity is the one minted for it;
5. the request carries the three public halves;
6. the request is signed by the key whose half it carries.

§ 4 then says *"nothing confidential crosses the enrollment path in either
direction"*. Presenting a secret would contradict that, because the enrollment
request is signed and not encrypted (`ADR-0005` § 7).

**As written, an implementation can generate the secret and ignore it, and pass
every case.** That is the shape of a check that cannot fail. C05 decides the
bundle's encoding, but not what the credential is:

| Option | Consequence |
|---|---|
| **The bootstrap credential is the secret**, and the token is an identifier | § 5 is already complete: the broker authenticates the bootstrap identity, and only the bundle holds its seed. § 1 and § 2 drop *"and secret"*. Nothing confidential crosses the path, as § 4 says |
| **The secret is a second factor**, presented and checked | The server stores a one-way verifier, never the secret. The request must carry it confidentially, but no key exists that the enrollment service could decrypt it with — `AST-8` is the result service's. § 4's sentence is then false, and a new key or class follows |

**Proposed: the first, by amendment in the prerequisite task.** It removes a
concept the protocol never used, rather than adding machinery to make it matter.
If the maintainer prefers the second, § 3.2 gains the verifier's storage, § 5.2
gains cases for presenting a wrong or missing secret, and the mutation matrix
plants an implementation that ignores it.

## 12. Scope this task must not absorb

- **Deciding `D-C05-1`.** That is key custody or an invariant, and either is an
  ADR or RFC change. C05 implements whichever is decided.
- **Deciding `D-C05-8` and `D-C05-9`.** Proposed as the same prerequisite task
  as `D-C05-1`. C05 consumes the TLS configuration that task produces and the
  credential definition it settles.
- **Re-enrollment, rotation and fleet recovery** — `ADR-0003` §§ 10, 11 and 13.
  C05 must not foreclose them; it does not build them.
- **Listing agents** — C10.
- **JetStream** — C06. Enrollment is core NATS by `ADR-0003` § 3, and C05
  creates no stream or consumer.
- **Any second journey verb** — C08 onward.
- **The agent's privilege split** — `ADR-0007` § 7 is C07's. C05's agent runs as
  whatever account C13 packages. The credential file's mode is C05's, and its
  owner is C07's and C13's.
