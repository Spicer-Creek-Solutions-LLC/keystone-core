**This dossier authorizes nothing.** It defines the boundary P01's plan will be
judged against. P01 still requires its own presented plan and its own explicit
approval, per [`AGENTS.md`](../../AGENTS.md) § 3.

Workstream text, normative in
[`REBOOT-EXECUTION-PLAN.md`](../project/REBOOT-EXECUTION-PLAN.md) § P01:

> Model operator, server service, agent, NATS operator, broker administrator,
> network attacker, compromised agent, compromised service credential,
> malicious command author, and supply-chain attacker. Document assets, trust
> boundaries, metadata leakage, denial/delay powers, key rotation, revocation,
> recovery, and accepted residual risk.

P01 is a planning task and may use one pull request; it does not split into

## 3. Exact outputs

One document, `docs/project/THREAT-MODEL.md`, containing:

1. Scope and method, naming what is modelled and what is explicitly not
2. Assets, each with the trust domain that owns it
3. Trust boundaries, enumerated, and the data flows that cross them
4. The ten actors, each with capabilities and motivations. The workstream's
   "compromised service credential" is modelled as *an attacker in possession
   of a compromised service credential* — the credential itself is an asset in
   § 2, not a party with motivations
5. Threats, each mapped to an actor, an asset, and a mitigation or an accepted
   residual risk
6. Metadata leakage — what an authorized broker observer learns without
   decrypting a payload
7. Denial and delay powers — what each actor can stall, drop or reorder
8. Key rotation, revocation and recovery
9. Accepted residual risk, each with owner, expiry and compensating control
10. What this model cannot tell you

Section 10 is not decoration. P00's evidence showed structural checks passing
semantic defects; a threat model that does not say where it is blind invites
the same error at a higher cost.

## 4. Requirement IDs

P01 writes no code. It **registers** rather than satisfies, and `AC-6`
requires **every one of the 24 invariants** in `ARCHITECTURE-INVARIANTS.md` to
map to at least one modelled threat *or* carry an explicit security-`N/A`
rationale.

An earlier draft enumerated fourteen "security-relevant" invariants. That
reproduced the problem it claimed to solve: it moved the judgement from review
time to dossier-writing time and froze it, and it omitted the delivery and
durability invariants — `ARCH-JOB-002`, `ARCH-JOB-003`, `ARCH-JOB-005`,
`ARCH-NATS-009`, `ARCH-NATS-010` — which is precisely where duplicate
execution, replay and redelivery-abuse threats live. Requiring all 24 with an
explicit waiver removes the curation step entirely.

P01 creates no new `ARCH-*` identifier. A new normative requirement requires an
RFC, per `REQUIREMENTS-TRACEABILITY.md` § Maintenance rules.

## 5. Acceptance cases

### 5.1 The TESTING.md feature table

All ten cases are `N/A`, per case. P01 touches no runtime boundary: it produces
one Markdown document and changes no executable path. The waiver rests on that
fact alone.

| Case | `N/A` because |
|---|---|
| Intended target | No agent exists and no command crosses a transport |
| Non-target | Same; there is no second agent |
| Server isolation | No server process exists |
| Authorization denial | P01 provisions no identity and writes no policy; P04 owns the first executable policy |
| Payload protection | No payload is constructed |
| Duplicate delivery | Nothing is delivered |
| Restart | No durable state is written |
| Cancellation/timeout | No process is started |
| Audit | The model *specifies* what must be auditable; specifying is not exercising |
| Diagnostics | Specification only, as above |

`TESTING.md` forbids waiving security cases "relevant to a touched boundary".
P01 is a security *document* and touches no runtime boundary; that this task is
about security does not make a runtime case applicable to it.

### 5.2 Document acceptance cases

| ID | Claim | Fails when |
|---|---|---|
| `AC-1` | All ten actors named in the workstream are modelled, each with capabilities and motivations, with compromised credentials modelled as an attacker wielding them rather than as a party | Any actor is absent, or present as a heading with no capabilities |
| `AC-2` | Every asset names the trust domain that owns it, and every data flow names the boundaries it crosses | An asset names no owning domain, or a flow names no boundary |
| `AC-3` | Every threat names a mitigation or is recorded as accepted residual risk | A threat resolves to neither |
| `AC-4` | Every accepted residual risk carries an owner, a **rationale**, a compensating control and an expiry | Any of the four is missing |
| `AC-5` | Metadata leakage, denial/delay powers, key rotation, revocation and recovery are each addressed in their own section | Any of the five is absent |
| `AC-6` | Every requirement in § 4 maps to at least one modelled threat, and every cited `ARCH-*` resolves | An enumerated requirement maps to nothing, or an identifier does not resolve |
| `AC-7` | No mitigation relies on a capability outside `v0.6.0` scope | A mitigation depends on a `Future / Unscheduled` capability |

`AC-4` takes all four elements from `TESTING.md` § Gate schedule — owner,
rationale, compensating control, expiry — matching the `D-01` precedent from
R10. An undated deferral is indistinguishable from having forgotten, and an
unexplained one is indistinguishable from not having looked.

### 5.3 Demonstrated failing, and what these cases cannot detect

Every case is demonstrated failing before acceptance, per
`REBOOT-EXECUTION-PLAN.md` § "Required task dossier". Evidence lands as
`docs/dossiers/P01-acceptance-evidence.md`.

**These cases are structural and will miss semantic defects.** That is stated
here rather than discovered in review, because P00 learned it the expensive
way: its suite passed three severity-1 semantic defects, and four of its own
checks were found wrong — three too loose, one too tight. The limits below are
an output of P01, not a retrospective:

All seven cases, with what would find the defect instead — the form this PR's
own amendment to the execution plan now requires. An earlier draft of this table
listed five cases and no "found instead" column, which is to say this dossier
did not satisfy the rule it introduces. That was caught in review, not by the
table.

| Case | Cannot detect | Found instead by |
|---|---|---|
| `AC-1` | Whether an actor's modelled capabilities are *realistic*, or whether an actor outside the ten is missing | Independent review; C14's adversarial suite later |
| `AC-2` | Whether the claimed owning domain is the *right* one, or whether a data flow is missing entirely | Independent review against the charter's journeys |
| `AC-3` | Whether a mitigation actually mitigates, as opposed to being named | Independent review; P02–P08 rejecting an unimplementable mitigation |
| `AC-4` | Whether a rationale is *sound*, or a compensating control effective | The maintainer accepting the risk, who owns it by name |
| `AC-5` | Whether a section's treatment is *adequate*, only that it exists | Independent review |
| `AC-6` | Whether the mapped threat is the one that invariant actually addresses, and whether a security-`N/A` waiver is honest | Independent review; the waiver rationale is the reviewer's primary target |
| `AC-7` | A mitigation relying on an unstated assumption rather than a named capability | Independent review; P11 when the assumption fails to appear in the skeleton |

Every entry says review, which is the point: § 8 names a reviewer rather than
deferring it, and the execution plan now states that a green acceptance suite
does not discharge that reviewer.

## 8. Security reviewer

**Codex, named here rather than at approval.**

Program rule 6 separates security-sensitive work from its acceptance review.
For P01 that is not a single section — the whole document is the security
artifact, so the drafting agent cannot review any of it. Naming the reviewer in
the dossier removes a merge-time block and reflects that Codex has now done
this work on P00 across three rounds, finding eight real defects including two
severity-1s that the acceptance suite passed.

The reviewer's remit is explicitly the semantic properties in § 5.3 that the
cases cannot reach. A green acceptance suite does not discharge it.

## 11. Decisions requiring confirmation at P01 approval

### `D-P01-1` — the threat model is a model, not an ADR

`docs/project/THREAT-MODEL.md`, not `docs/adr/000N-*`. P02 onward are ADRs
because they decide between options; P01 describes a world. `SECURITY.md`
already names it as the deliverable.

### `D-P01-2` — findings against the charter are raised, not fixed

If modelling shows a canonical journey is unsafe as specified, P01 records the
finding and stops. The charter is accepted and its own task's output; amending
it silently inside P01 would let a security review rewrite the product scope it
was reviewing.

## 12. Scope this task must not absorb
