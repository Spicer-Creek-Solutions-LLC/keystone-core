## Code of Conduct

This project follows the [Contributor Covenant Code of Conduct](https://www.contributor-covenant.org/version/2/1/code_of_conduct/).
By participating, you agree to uphold this code. Report unacceptable behavior
to the project maintainers.

## Getting Started

### Prerequisites

- Go 1.21 or later
- Git
- Make (optional, for convenience targets)
- Docker/Podman (for E2E tests)

### Setting Up Your Development Environment

1. Fork the repository on GitHub

2. Clone your fork:
   ```bash
   git clone https://github.com/YOUR_USERNAME/keystone-core.git
   cd keystone-core
   ```

3. Add the upstream remote:
   ```bash
   git remote add upstream https://github.com/ORIGINAL_OWNER/keystone-core.git
   ```

4. Install dependencies:
   ```bash
   go mod download
   ```

5. Build the project:
   ```bash
   make build
   # or: go build ./...
   ```

6. Run tests:
   ```bash
   make test
   # or: go test ./...
   ```

## How to Contribute

### Reporting Bugs

Before creating a bug report:
- Check the existing issues to avoid duplicates
- Collect information about the bug (version, OS, steps to reproduce)

When filing a bug report, include:
- A clear, descriptive title
- Steps to reproduce the behavior
- Expected behavior vs actual behavior
- Relevant logs or error messages
- Your environment (OS, Go version, Keystone Core version)

### Suggesting Features

We welcome feature suggestions! Please:
- Check existing issues and discussions first
- Describe the use case and problem you're solving
- Explain your proposed solution
- Consider implementation complexity and alternatives

### Contributing Code

1. Find an issue to work on, or create one for discussion
2. Comment on the issue to let others know you're working on it
3. Fork and create a feature branch
4. Make your changes following our coding standards
5. Add tests for new functionality
6. Submit a pull request

## AI-Assisted Contributions

**This project accepts AI-assisted contributions.** We require transparency
and human accountability. See [AI-CONTRIBUTIONS.md](AI-CONTRIBUTIONS.md) for
complete details.

### Quick Summary

1. **Disclose AI usage** in your commit message:
   ```
   🤖 Generated with [Claude Code](https://claude.com/claude-code)

   Co-Authored-By: Claude <noreply@anthropic.com>
   ```

2. **Review and test** all AI-generated code before submitting

3. **Take responsibility** for the contribution as if you wrote it yourself

4. **Check the PR template** boxes confirming AI disclosure

### What Counts as AI-Assisted

- Code generated by AI tools (Claude, GPT, Copilot, etc.)
- Documentation drafted by AI
- Test cases generated by AI
- Any content where AI produced the initial draft

## Development Workflow

### Branch Naming

Use descriptive branch names:
- `feat/add-user-authentication`
- `fix/nats-reconnection-bug`
- `docs/update-getting-started`
- `refactor/simplify-state-module`

### Commit Messages

Follow conventional commit format:

```
type(scope): short description

Longer description if needed.

🤖 Generated with [Tool] (if applicable)

Co-Authored-By: ... (if applicable)

Signed-off-by: Your Name <your.email@example.com>
```

Types:
- `feat`: New feature
- `fix`: Bug fix
- `docs`: Documentation only
- `style`: Code style (formatting, semicolons, etc.)
- `refactor`: Code change that neither fixes a bug nor adds a feature
- `perf`: Performance improvement
- `test`: Adding or updating tests
- `chore`: Maintenance tasks

### Keeping Your Fork Updated

```bash
git fetch upstream
git checkout main
git merge upstream/main
git push origin main
```

## Coding Standards

### Go Style

- Follow [Effective Go](https://golang.org/doc/effective_go.html)
- Run `gofmt` on all code
- Run `go vet` and address warnings
- Use meaningful variable and function names
- Add comments for exported functions and types

### Error Handling

- Always handle errors; don't ignore them
- Wrap errors with context using `fmt.Errorf("context: %w", err)`
- Use custom error types for domain-specific errors

### Logging

- Use structured logging
- Include relevant context (correlation IDs, operation names)
- Use appropriate log levels (debug, info, warn, error)

### Security

- Never commit secrets, credentials, or API keys
- Validate all inputs, especially from external sources
- Follow OWASP guidelines for secure coding
- Use parameterized queries to prevent injection

## Testing

### Running Tests

```bash
# All tests
make test

# Specific package
go test ./pkg/state/...

# With coverage
go test -cover ./...

# With race detection
go test -race ./...
```

### Writing Tests

- Write table-driven tests when testing multiple cases
- Use meaningful test names: `TestFunctionName_Condition_ExpectedResult`
- Include both positive and negative test cases
- Mock external dependencies
- Aim for >70% coverage on new code

### E2E Tests

```bash
# Requires Docker
KSCORE_E2E_TESTS=1 make e2e-test
```

## Pull Request Process

### Before Submitting

- [ ] Code compiles without errors
- [ ] All tests pass
- [ ] New code has tests
- [ ] Documentation is updated if needed
- [ ] Commit messages follow our format
- [ ] AI usage is disclosed (if applicable)
- [ ] DCO sign-off is present

### PR Description

Include:
- Summary of changes
- Related issue numbers
- Testing performed
- Screenshots (for UI changes)
- AI disclosure checkbox

### Review Process

1. Maintainers will review your PR
2. Address any requested changes
3. Once approved, a maintainer will merge
4. Delete your branch after merge

### What We Look For

- Code quality and readability
- Test coverage
- Documentation
- Security implications
- Performance considerations
- Backward compatibility

## Developer Certificate of Origin

By contributing, you agree to the [Developer Certificate of Origin](DCO.md).
Sign off your commits:

```bash
git commit -s -m "Your commit message"
```

This adds a `Signed-off-by` line certifying you have the right to submit
the contribution under our license.
